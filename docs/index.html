Git remembers what changed. memorycastle remembers why.

Not version control: the project's history of decisions. Every agent and every session adds what it decided, rejected and measured, so the next one steers the way the last one was going instead of rediscovering it. Like Git, it is worth more the longer a project runs.

One 6 MB Rust binary, one SQLite file, no LLM, no key, no server. Claude Code, Codex, Gemini CLI, Cursor and the rest forget everything between sessions. memorycastle keeps, per repository, what was decided, what was rejected, what was measured, and the exact lines of code it lives in. On five questions about the rushtex repository, every answer was right with and without it, and with memorycastle the same answers cost 48% less on Fable, 28% on Opus and 25% on Sonnet, in half the turns.

Cut AI coding agent API costs by up to 48%

Claude Code, Codex, Gemini CLI and Cursor bill by the token, and most of those tokens go into rediscovering what the project already knows. memorycastle gives every coding agent a persistent memory of the repository, so it pays for the answer, not for the search. On Claude Fable 5.1 it lowered the API bill by 48%, on Opus 5.5 by 28% and on Sonnet 5.5 by 25%, with every answer right.

Where the API bill goes

Each turn of an agent sends its whole context back to the model. A question about code that the agent answers by searching costs a turn for every grep, every file it opens and every guess it corrects, and each turn re-reads everything before it. On a large model each of those turns is billed at a large model's price. The expensive part is rarely the answer; it is the loop that finds it.

How persistent memory lowers it

Decisions answered in one call
What the project decided, rejected and measured is written down by the agent that did the work, with the numbers. The next agent finds the note instead of re-deriving the decision from code, comments and history.
Exact lines, not whole files
memcastle links returns where a function is defined (path:start-end), every caller and the notes about it. The agent reads 40 lines instead of a 1,000-line file and skips the grep-and-read rounds.
No repeated mistakes
The costliest tokens are the ones spent rebuilding something the project already tried and rejected. The memory puts that rejection in front of the agent before it starts.
Half the turns
In the benchmark the agents needed half as many turns on every model: 45 to 21 on Fable, 30 to 15 on Opus, 21 to 12 on Sonnet. Fewer turns means fewer times the context is billed.
No LLM of its own, no API key
Indexing and search run locally in a 6 MB binary with a small embedding model on the CPU. Saving a note costs 0 tokens; the only cost to the agent is about 600 tokens of fixed context per session.

How to use links

Run it before an edit, on the function or file about to change: memcastle links render::search. One call returns where the definition is (path:start-end), every caller with every line it calls from, what it calls, and the notes and decisions about it. Read the printed range, not the file; edit the call lines it lists; respect the decisions it quotes.

defined: src/tripwire.rs:161-196  (fn)
   called by: 2  check src/gate.rs:164 0.7, run src/main.rs:1185,1257 0.7; complete for direct calls, not through traits, macros or pointers
memorycastle/journal/2026-10-22-rejected-approach-tripwire.md  An edit that brings back an approach a linked note rejected is told so
   decision   ...
Method
Claude Code in headless mode with no user settings, one run per arm and question, each in a fresh copy of the repository, every run starting with a cold prompt cache. An answer is right when it reaches the recorded decision; for n4 and n5 it must also name the call sites.
Scope
Each question is a fresh session, so the plugin's fixed context is paid on every question; in a working session it is paid once.

How it works

Four steps, nothing invented. The notes are the memory. Everything else is derived from them and can be rebuilt from the repository alone.

1. The agent writes a note
At the end of a task that changed a decision: Context, Decision, Rejected, Measured, in memorycastle/journal/, committed with the code. Written in the session that did the work, with the numbers still in hand.
2. The store indexes it
Split by heading, indexed for keywords with SQLite FTS5, embedded with a local EmbeddingGemma 2 model, int8, on the CPU. No API key, no network after the first download.
3. A question gets a paragraph and a line range
Keyword and meaning results are fused, judged for confidence, and reranked by what the note declares it is about. Each hit names the lines of the note that matched, each part with its own confidence, and the answer ends with path:start-end spans of code: the lines to read, not the files. It learns from use: a note read after a search that ranked it lower keeps the question, so the next wording finds it first.
4. Hooks keep it honest
Recall on every prompt, the right notes before every edit, a read guard, a silent read ledger, and the note asked for at the moments it is due. In Claude Code, Codex, Gemini CLI and Cursor.

The answer: a fixed grammar, for eyes and parsers alike

A hit line with the note's matching lines, confidence and section, then label value fields, a blank line, then a lettered table of code spans to read first. By default a hit is one line, the note's Decision sentence and lines: the note's other matching parts, each with its own confidence, so the agent reads those lines and not the whole note. On 83 title questions the Decision section was among them 76 times; the hit line alone pointed at it 20 times. --sections opens the one you picked.

Memory that says "check me": a note knows when its code changed

At save, the store hashes the body of every function the note names. At search, a note whose function has since changed is labelled and ranked under one whose code still matches. Deterministic: the hash then against the hash now. The agent is told to read those lines before trusting the paragraph.

1. ...honest-savings.md:71   0.82   Open
2. ...constant-uses.md:6     0.77   Context  code changed since: is_identifier_use

A number that can go down

The status line shows tokens saved this session. It is not a running total. Every time it draws, it is recomputed from the ledger for the whole session.

saved = bytes the printed spans stood in for
        − bytes of those reads
        − bytes of every lookup this session printed

It falls when a lookup leads to no read, since the third term grows and nothing offsets it, and when a guided read is followed by reading the same file whole, which is cancelled and counted. It rises when a printed span stands in for a file the agent would have read. Idle time, saving notes and silent hooks never move it. A number that can go down is one you can believe when it goes up; if it turns negative, the tool costs more than it saves and the status line says so.

The note happens at the moments it is due

No human reminds the agent. The hooks do, from the edits ledger, not from reading the chat, so they cannot nag when nothing was edited.

Every prompt

Happens. Recall: when the journal is confident about the topic, one line per note with its Decision sentence, each note once per session. Mid-session, once, when five files were edited or thirty minutes passed since the last note, then quiet for thirty minutes.

Why then. The session that would not have searched still sees the note; the one that searches sees nothing new.

After a commit

Happens. One line with the files edited since the last note; the agent writes it or ignores it.

Why then. A task just closed and the facts are still in context.

Before compaction

Happens. The agent is held once with the reason and a draft; the second attempt passes, so nothing can wedge.

Why then. The why is about to be summarised away.

At stop

Happens. The same hold, once. If no decision was made, the agent says so and stops.

Why then. The turn is ending; after it, nobody writes the note.

Claude Code through its plugin; Codex, Gemini CLI and Cursor through memcastle hook, wired by install. Copilot, OpenCode and Antigravity have no hook surface and get the instructions and the tools.

Where it is, who calls it, what we said about it. One call.

Every save reads the note for the files and symbols it names in backticks and keeps them as edges. Every checkout gets a code index: definitions with their end line, imports and call edges by name, built by scanning lines, with no parser, no model and no LLM.

Languages: Rust, Kotlin, Java, Python, TypeScript and JavaScript, Go, Swift, Ruby, PHP, C# and C/C++. C is read by its own grammar and finds 98% of what ctags finds on six real C and C++ trees; Go, Java, TypeScript and Python find 99% to 100% of the functions and types their own parsers find. links answers from both at once, and from the code alone when no note exists yet.

Run memcastle links upsert_snippet

defined: src/install.rs:116-120  (fn)
   called by: 6  install_section src/install.rs:248 0.9, snippet_added_refreshed_and_left_alone src/install.rs:714 0.9 +4 more
   calls: 1  upsert_section

Read it as. Read those five lines, not the 760-line file. The callers are what you will break; the tests are named so you know which ones to run. The number after a caller is how likely that call reaches this definition, measured on history: when a signature changed, the share of call sites the same commit updated. 1.0 for self.f( or a bare call in the same file, 0.9 for a name defined once, down to 0.2; under 0.3 a call is counted, not listed.

Why it helps, and what it does not do

Helps: reading less
A definition is 5 to 70 lines; the file around it is 700 to 1,300. The ledger on this repo: 24 reads guided by a span read 50 KB of files that total 956 KB.
Helps: knowing before breaking
Callers come with the definition, so a signature change is a list, not a search. Twice in one day an answer disagreed with what the agent believed; both times the answer was right and a bug was found.
Helps: names you do not have
A grep needs the exact identifier. links takes a file and a line, or a symbol, and the notes about it come without any text match, because the save made the edge.
Helps: change detection
A note stores the hash of each definition it names; when the body changes, search labels the note code changed since and ranks it under one whose code did not move.
Does not: resolve dispatch
A call through a trait, a macro or a dynamic dispatch is not resolved. Edges are by name. For an exact call graph use a language server; this is the 2 ms answer that is right often enough to read first.
Does not: infer
No edge is guessed from similarity. A file is linked to a note because the note named it. The HTML view in memorycastle/graph/ draws exactly the rows in the TSVs.

Case studies: one working session, recorded as it happened

On 2026-10-25, with release 0.11.52 just installed, the agent that builds memorycastle used it on three real code bases: a private messaging app (930 files of Rust, Kotlin and TypeScript), rushtex (a TeX engine in Rust) and memorycastle itself. Below are the commands it ran, the output it got, the byte counts, and what it would have taken without the tool. The two cases where the tool fell short are included.

1. Who calls this method, and whose method is it?

Ran memcastle links BapCodec::encode_hybrid_auth_proof in the messaging app

defined: crates/dcp-core/src/bap.rs:376-391  (fn in BapCodec)
   called by: 5  hybrid_proof_is_exact_bounded_and_versioned crates/dcp-core/src/bap.rs:639 0.7,
                 create_hybrid_auth_proof crates/mobile-core/src/bap_auth_client.rs:151 0.7,
                 create_hybrid_auth_proof_frame crates/mobile-core/src/bap_auth_client.rs:186 0.7, +2 more
   calls: 1  reserve_frame

Result. 617 bytes: the span to read, the type that owns the method, every caller named by the function it sits in, and what it calls. A grep for the same name returned 732 bytes of matching lines, and the reader still had to work out which function each line belongs to. The caller list matched grep's call sites one for one.

2. The agent guessed the name wrong

Result. 272 bytes and the right name on the first line. A grep for the guessed name finds nothing and leaves the agent to guess again. The suggestion is printed only when the guessed name's words all appear in the real one, so a wild guess gets silence, not a wrong lead.

Across names with two or more definitions, a qualified lookup now prints exactly one definition 86% of the time on the messaging app and 98% on rushtex, up from 58% on both.

4. A plain grep, answered before it ran

Ran grep -rn skip_generics src in memorycastle

memorycastle answered this search with `links skip_generics` (once; the same search runs if you retry it):
defined: src/code.rs:2146-2166  (fn)
   called by: 1  owners src/code.rs:2107 0.9; complete for direct calls, not through traits, macros or pointers

Result. The hook saw a search for one name the code defines and returned the definition and its only caller instead. It fires once per name per session; a second identical grep runs normally. Replayed over 14,410 past greps it fired on 0.8% of them, about seven in eight genuine name lookups.

5. Editing a file with history

Happened on the first edit of src/db.rs, with no command typed

memorycastle: src/db.rs; what is known about it (read the ranges that matter):
memorycastle/journal/2026-10-25-method-owner.md  Each method knows its owner type ...
   decision   Schema v29: `code_defs.owner`, filled at index time by `code::owners` ...

Result. The decision the edit was about to touch arrived with the edit, in two lines. After the commit, the same hooks pointed out that the session's note did not list two of the files changed for it; the note was corrected before the session moved on.

6. Using it found a bug in it

Happened on the first session start after upgrading to 0.11.51: table code_defs has no column named owner

Result. Several memorycastle processes start together at session start, and the schema upgrade ran without a lock, so one process undid part of another's upgrade. Release 0.11.52 runs every upgrade under the database's write lock and repairs a store that 0.11.51 left in that state. Eight processes started at once, three times, upgraded cleanly. The fix shipped the same hour.

7. Where it fell short: a very common name

links verify printed 3.6 KB for its ten definitions, most of it the same "+51 by name only" count repeated under each. The definitions and owners are the useful part. Fixed in 1.0.0: the counts and the "complete for direct calls" note are said once after the definitions; the same lookup is 2.7 KB (−26%).

8. Where it fell short: a question no note answers

memcastle search "why does BAP use a hybrid Ed25519 and ML-DSA proof" ranked first, at 1.00, a bug-tracker line that names both algorithms but records no decision. No note in the messaging app explains that choice, and the honest answer is "nothing written down". A verbatim identifier counts as proof of relevance, which is what makes exact-name searches dependable, and here it lifted a mention over an absence. Changed in 1.0.0: such a hit now reads 1.00 ... name match, by meaning 0.40, so the 1.00 is visibly a name, not an answer. A line saying "no note records a decision" was built and measured, and not shipped: on 182 gold questions that do have a recorded answer it fired on 51 (28%), and a narrower version on 15 (8%), while missing this very case. Word overlap cannot tell a note that mentions a topic from one that decides it.

Verdict
For navigating code, finding a definition, its owner, its callers and the notes about it, the tool answered in one call what otherwise takes a grep and a reading pass, and it recovered from wrong names. For decisions it is exactly as good as the notes behind it; where none exists, it should say so more plainly. Case 7 is fixed and case 8 is labelled; telling "mentions" from "decides" remains open.

A week on a large project: Mira, a payments monorepo, three agents

A made-up team, a real tool: every command and number below is what memorycastle does today. Mira's company has one big repository with 4,000 files, nine people, and AI coding agents that forget everything when a session ends.

How it started

Mira reads about memorycastle: a memory for AI coding agents. An agent writes down what it decided and why at the end of each task, and the next agent, on any machine, finds that note before it repeats the work. Fewer wrong turns, fewer tokens. What convinces her: it is one small Rust program, it uses Google's EmbeddingGemma 2 model to understand meaning, it runs fully offline once installed, it needs no account and no API key, and it uses a fraction of the memory of the alternatives. She tries it on her own laptop:

curl -fsSL https://raw.githubusercontent.com/abhksinha/MemoryCastle/main/scripts/get.sh | sh
memcastle install

The second command finds Claude Code, Codex and Cursor on her machine and connects each one. Inside the company repository it reads the 4,000 files and learns where every function is, in four seconds. It also reads her last month of agent chat logs, so the savings counter starts with a history instead of zero. There are no notes yet; her status line says 0 notes.

Monday afternoon
Mira asks Claude to move "settlement retries" from a timed job to a queue. Forty minutes in, five files have changed, and memorycastle quietly tells Claude it owes a note. Claude writes it in the repository: the queue was chosen because retries must survive a deploy; a Redis stream was tried and dropped because it could not keep one customer's events in order; the slow-request number before and after. The note is a plain Markdown file. It is committed with the code, like any other file.
Tuesday
Dev, a teammate, pulls the repository and opens Codex. He asks it to "make settlement retries faster by batching". Before Codex answers, memorycastle shows it one line: Mira's note, with the sentence about the Redis stream that was rejected. Codex reads the forty lines of code the note points to and proposes batching inside the queue instead of adding a second stream. Nobody told Codex about Monday. The note did.
Wednesday
Priya edits a 2,400-line file that eleven notes mention. As her agent starts the edit, memorycastle finds the one function she is changing and shows only the two notes about that function, with the 180 lines it lives in. Her agent reads those, not the whole file. When it tries to read the whole file anyway, memorycastle stops it once and gives it the exact lines to read instead. Her status line that evening: ~41k (58%) this session, tokens not spent.
Thursday
Someone rewrites that same function. The next time a search returns Priya's note, it is marked code changed since: post_batch and ranked below notes whose code is still the same. Her agent reads the new code before trusting the old note, finds the rule still holds, and writes a one-line note saying it checked. Mira's note about retries is untouched, because its code did not change.
Friday
A long session runs out of room, and the agent is about to compress its own memory of the conversation. memorycastle holds it once and asks for the note first, with a draft already filled in from the files it edited. The agent writes the decision and the numbers while it still remembers them, saves, and carries on. The status line shows the week: ~310k (66%) last 7 sessions. On Friday that number fell by 3k while an agent searched four times for something nobody had written down. The team sees that too, and someone writes the missing note.
What never happened
Nobody set up a server, pasted a key, uploaded a chat log, or explained a graph. Nine people pulled a folder of Markdown files, and their agents stopped making the same decision twice. On each laptop the memory is one file under ~/.local/share/, rebuilt from the repository if it is ever deleted.

The words on this page

Short definitions of every term the tables use, in the order you meet them.

Turn
One call to the model: the agent sends its context, the model answers or asks for a tool. Every turn bills the context again, so fewer turns is a smaller API bill.
Prompt cache
Context the provider has seen recently is billed at a fraction of the input price; context seen for the first time is written to the cache at a higher price. The benchmark started every run with a cold cache so neither side was helped.
Note
One Markdown file in memorycastle/journal/, written by an agent or a person at the end of a task: a title, author and date, the files it is about, and sections for Context, Decision, Rejected, Measured and Open. The notes are the memory; everything else is derived from them.
Journal
All the notes of one repository. "Project 1, 48 notes" is a journal of 48 files.
Chunk
A piece of a note the index works on: one section, split further at about 60 words. A hit points at a chunk and prints its line number.
Keyword search
BM25 over the chunks through SQLite FTS5. No model is loaded; under 3 ms from a 9 MB process. Used alone when an identifier from the question is found verbatim.
Meaning search
The question and every chunk as vectors from a local embedding model (EmbeddingGemma 2, 300M parameters, int8); ranked by cosine similarity, fused with BM25. 52 ms warm, 300 MB while the model is loaded.
Confidence
A number from 0 to 1 printed on every hit: the model's cosine rescaled between a floor and a ceiling set on a gold set, reduced when the question's rare words are absent from the chunk. Under 0.30 the hit is dropped and the answer is "no relevant note". An identifier found verbatim is 1.0.
Gold set
A private list of real questions about a journal with the note that answers each, plus questions whose right answer is nothing. Every retrieval number on this page is scored against one.
Superseded note
A note replaced by a later one, declared by the newer note's Supersedes: line. It is kept, labelled and ranked below its replacement, never edited or deleted.
Read spans
The path:start-end lines after every answer: the definitions the question or the top notes name, re-found by their anchor line if the file has changed since indexing. The agent reads those lines, not the file.
Ingest
Building the index from the notes: hash, split, FTS5, one embedding per chunk. Re-index: the same for one edited note, with unchanged chunks carried over.

One repo, one memory

Every call works out the project from the current directory: the git root, and the remote normalised to host/owner/repo. A fresh clone on another machine is the same project; a worktree is the same as its main checkout. Each query binds that project before ranking, so a search in one repo can never return another repo's note.

Sister repos

Declare a group once per repo with memcastle project group <name>; then search --related includes the siblings, labelled and down-weighted so the home repo wins ties.

Without a group, --related searches nothing and says how to declare one. Isolation stays the gate.

Repos without a remote

The project is keyed by the directory path, so moving the directory starts a new project. Add a remote and it binds to that instead.

With a remote, a move or a second clone changes nothing.

Teammates

They get the notes by pulling the repo. Their first memcastle install on a machine wires the agents; inside the repo it indexes the notes.

No server, no account, no sync.

What is never searched

There is no "everything I know". A question about another repo is answered in that repo or through a declared group.

The isolation is a test in the suite, not a setting.

Start

Two lines install it; the rest are the commands you will use first.

curl -fsSL https://raw.githubusercontent.com/abhksinha/MemoryCastle/main/scripts/get.sh | sh
memcastle install                 # every agent on this machine, from any directory
cd your-repo && memcastle install # also this repo: journal, code index, past transcripts
memcastle search "why did we pick int8"
memcastle links src/store.rs
memcastle guide                   # the instructions an agent follows
memcastle uninstall --purge       # the reverse, notes stay
Prerequisites
macOS Apple silicon or Linux x86_64 (prebuilt), otherwise Rust 1.85 and cargo.
Model
EmbeddingGemma 2, downloaded once with a pinned checksum. Everything lands under ~/.local/.
Codex
Codex asks you to trust the hooks once with /hooks.
